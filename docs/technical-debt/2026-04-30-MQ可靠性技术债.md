# MQ 可靠性与环境隔离技术债

## 1. 背景

2026-04-30 本地启动 `backend-java` 时，服务连接远程 RabbitMQ 后消费到 `agent.parse.result.v1` 中的历史解析结果消息。消息中的 `jobId` 在当前 Java 服务连接的数据库中不存在，导致 `ParseResultConsumer` 记录 `parse job not found`。

RabbitMQ Web UI 随后显示 4 个队列均为空：

- `agent.generate.request.v1`
- `agent.generate.result.v1`
- `agent.parse.request.v1`
- `agent.parse.result.v1`

这说明问题不是队列当前仍有积压，而是历史消息已经被消费者消费并确认。当前链路可概括为：

```text
Java 本地服务连接远程 RabbitMQ
-> 消费 agent.parse.result.v1 历史 result 消息
-> result 中 jobId 在当前数据库不存在
-> ParseResultConsumer 报 parse job not found
-> 异常被 catch 后方法正常返回
-> Spring AMQP 自动 ack
-> RabbitMQ 队列被消费空
```

## 2. 现象

- Java 启动日志出现 `ResourceNotFoundException: parse job not found`。
- RabbitMQ Web UI 显示相关队列 `Ready=0`、`Unacked=0`、`Total=0`。
- 日志中的错误发生在历史消息消费阶段，不代表当前 RabbitMQ 仍有脏数据。
- 本次问题暴露出 MQ 确认、重试、死信、事务一致性和环境隔离机制不完整。

## 3. 当前实现概述

- `backend-java` 使用 Spring AMQP `@RabbitListener` 消费 result 队列。
- `backend-agent` 使用 `aio-pika` 消费 request 队列，并发布 result 消息。
- `RabbitTopologyConfig` 只声明普通 durable classic queue，没有显式 retry queue 或 DLQ。
- `ParseRetryScheduler` 提供业务层 parse job 重试，但它不是 RabbitMQ 层面的消费失败重试。
- `ParseJobService.create()` 在数据库事务内直接发布 parse request 消息，存在 DB 事务与 MQ 发布一致性风险。

## 4. 技术债清单

| 编号 | 严重级别 | 当前表现 | 代码证据 | 影响 | 推荐治理方式 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- |
| TD-MQ-001 | 高 | 消费端异常确认语义不清晰，异常被 catch 后方法正常返回会触发 ack | `ParseResultConsumer.consume()` | 可恢复异常可能被当作消费成功，消息丢失；不可恢复脏消息又缺少独立审计 | 按异常类型区分 ack / nack / DLQ；未知 jobId 等不可恢复消息 WARN 后 ack | P0 |
| TD-MQ-002 | 高 | RabbitMQ 拓扑缺少 DLQ / retry queue | `RabbitTopologyConfig` | poison message、临时故障和异常消息没有统一隔离位置 | 为 request/result 队列配置 retry queue 和 DLQ | P0 |
| TD-MQ-003 | 高 | Java 在 DB 事务内直接发布 MQ request | `ParseJobService.create()`、`ParseRequestPublisher.publish()` | MQ 消息可能早于 DB commit 被消费；事务回滚后可能产生孤儿消息 | 引入 Transactional Outbox 或事务提交后发布机制 | P1 |
| TD-MQ-004 | 中 | Python Agent 消费 request 使用 `requeue=False`，失败处理偏粗 | `backend-agent/app/mq/consumer.py` | Agent 发布 result 前崩溃时，request 可能被丢弃，Java 侧不一定能感知 | 区分可恢复和不可恢复异常；可恢复异常进入 retry / DLQ | P1 |
| TD-MQ-005 | 中 | 业务重试与 MQ 重试边界不清 | `ParseRetryScheduler`、`ParseJobService.applyParseResult()` | parse 业务失败可重试，但 MQ 消费失败、DB 写失败、发布失败缺少独立策略 | 明确业务失败由 parse job 状态机处理，基础设施失败由 MQ retry / DLQ 处理 | P1 |
| TD-MQ-006 | 高 | 远程 MQ 缺少环境隔离，多个环境可能共用 vhost `/` 和固定队列名 | `.env`、`application.properties`、Agent MQ 配置 | 不同数据库环境的 jobId 可能串入同一 result 队列，产生脏消息 | 使用独立 vhost 或 queue prefix 区分 dev/test/prod/office | P0 |
| TD-MQ-007 | 中 | 缺少消息级幂等与可观测性 | result 消费链路、publisher | 重复消息、乱序消息、未知消息难以追踪；只能依赖日志排查 | 增加 messageId / traceId / jobId 指标、幂等记录、DLQ 告警 | P2 |

## 5. 影响范围

- `backend-java` 解析任务创建、结果消费、状态流转、失败重试。
- `backend-agent` 解析请求消费、生成请求消费、结果消息发布。
- RabbitMQ 队列：
  - `agent.parse.request.v1`
  - `agent.parse.result.v1`
  - `agent.generate.request.v1`
  - `agent.generate.result.v1`
- 运维与排障：队列为空不代表没有发生过脏消息消费；日志和消息确认语义需要结合判断。

## 6. 根因分析

这不是完全没有消费确认机制。当前系统已经有基础消费、自动确认、durable queue 和 parse job 业务重试。

真正的问题是：确认、异常分类、重试、死信、事务一致性和环境隔离没有形成完整可靠性模型。

本次队列为空的原因是消费者 catch 异常后正常返回，Spring AMQP 将消息视为处理完成并 ack。该行为对清理未知 `jobId` 的历史脏消息有帮助，但如果同样发生在数据库临时故障、MQ 发布失败等可恢复异常上，就可能造成消息丢失。

当前应区分三类消息：

| 类型 | 示例 | 期望处理 |
| --- | --- | --- |
| 不可恢复消息 | JSON 非法、UUID 非法、未知 jobId、schema 不支持 | WARN / 审计后 ack，必要时进入 invalid DLQ |
| 业务失败结果 | Agent 返回 `status=FAILED`、`EXT_OSS_UNAVAILABLE` | ack result，更新 parse job 为 FAILED，由业务重试调度处理 |
| 基础设施临时失败 | DB 短暂不可用、事务提交失败、MQ 发布失败 | 不吞异常，进入 MQ retry / DLQ |

## 7. 短期治理方案

1. 未知 `jobId`、非法 JSON、非法 UUID 作为不可恢复消息处理，记录 `WARN` 后 ack。
2. DB 临时异常、MQ 发布异常不能被通用 catch 吞掉，应进入 retry / DLQ。
3. 给 result 队列配置 DLQ，至少保证失败消息可追踪。
4. 给不同环境配置独立 RabbitMQ vhost 或 queue prefix，避免本地、测试、远端环境串消息。
5. 增加 `QUEUED` / `RETRYING` 超时补偿，避免 Agent 在发布 result 前失败导致任务长期卡住。

## 8. 中期治理方案

1. 引入 RabbitMQ retry queue + DLQ：
   - 主队列处理正常消息。
   - retry queue 通过 TTL 延迟后回投主队列。
   - 超过最大次数进入 DLQ。
2. Java result consumer 按异常分类处理 ack / nack。
3. Python Agent request consumer 区分可恢复和不可恢复异常。
4. 发布消息启用 publisher confirm 或等效失败感知，避免静默发布失败。
5. 增加消息 schema 校验，校验 `traceId`、`jobId`、`tenantId`、`schemaVersion` 的一致性。

## 9. 长期治理方案

1. Java request 发布引入 Transactional Outbox：
   - 业务事务内写 parse job 和 outbox event。
   - 事务提交后异步发布 MQ。
   - 发布成功后标记 outbox event 已发送。
2. result 消费增加消息幂等表或幂等键，防止重复 result 造成重复写入或重复触发生成任务。
3. 建立 MQ 可观测性指标：
   - DLQ 数量
   - retry queue 数量
   - `parse job not found` 数量
   - `QUEUED` / `RETRYING` 超时数量
   - result 消费成功率和失败率
4. 建立环境隔离规范：dev / test / prod 不共用 vhost 和队列。

## 10. 验收标准

- 远程 MQ 中的历史 result 消息不会导致 Java 服务启动被误判为失败。
- 未知 `jobId` 消息有明确处理策略和日志级别。
- 可恢复异常不会被通用 catch 静默 ack。
- RabbitMQ 中存在可观测的 DLQ 或等效失败隔离机制。
- 不同环境的 MQ 消息不会进入同一个业务队列。
- parse job 长时间卡在 `QUEUED` / `RETRYING` 时有补偿或告警。

## 11. 风险与注意事项

- 不应简单地把所有异常都 requeue，否则未知 `jobId`、非法 JSON 等 poison message 会形成无限重试。
- 不应简单地把所有异常都 catch 后 ack，否则数据库或 MQ 临时故障会造成消息丢失。
- 清空 RabbitMQ 队列是破坏性操作，只能在确认没有正常待处理消息后执行。
- 改造 DLQ / retry queue 可能需要变更 RabbitMQ 拓扑，必须考虑已有队列参数不可原地变更的问题；必要时使用新队列名或先删除重建。
- 引入 outbox 会增加数据库表和调度任务，需要单独设计迁移和补偿策略。

# 报告分析生成幂等技术债

## 1. 背景

2026-05-01 排查 `/api/records/{recordId}/analysis` 报错时，日志中同时出现两类现象：

- `context not ready: recordId=... jobId=...`
- `DuplicateKeyException: duplicate key value violates unique constraint "generated_outputs_record_id_type_version_key"`

其中 `context not ready` 表示记录解析上下文尚未满足分析条件；`DuplicateKeyException` 表示报告分析结果写入 `generated_outputs` 时违反唯一约束。

两者可能在同一次上传或切换记录过程中相邻出现，但不是同一个直接根因。当前需要记录的核心技术债是：报告分析生成链路缺少并发幂等保护，多个并发请求可能同时生成同一条记录的 `REPORT_ANALYSIS` 第 1 版。

## 2. 现象

- Java 日志出现未处理异常，最终由 `ApiExceptionHandler` 记录为 `Unhandled API exception`。
- PostgreSQL 返回唯一键冲突：

```text
ERROR: duplicate key value violates unique constraint "generated_outputs_record_id_type_version_key"
Detail: Key (record_id, type, version)=(..., REPORT_ANALYSIS, 1) already exists.
```

- 报错链路指向：
  - `RecordController.getRecordAnalysis()`
  - `ReportAnalysisService.getOrGenerate()`
  - `GeneratedOutputService.createGeneratedOutputWithMeta()`
  - `GeneratedOutputMapper.insertWithJsonMeta()`
- 用户侧可能看到分析接口失败，但数据库中实际已经存在同一记录的 `REPORT_ANALYSIS` 结果。

## 3. 当前实现概述

当前 `/api/records/{recordId}/analysis` 是读写混合接口：

```text
GET /api/records/{recordId}/analysis
-> 查询 generated_outputs 中是否已有 REPORT_ANALYSIS
-> 没有缓存时，读取解析上下文
-> 若 parseStatus=SUCCESS 且 structuredResult.payload.fields 非空，则调用 agent 生成分析
-> 通过 nextVersion(recordId, type) 查询最新版本号
-> 插入 generated_outputs
```

`generated_outputs` 表当前有唯一约束：

```sql
UNIQUE (record_id, type, version)
```

`GeneratedOutputService.nextVersion()` 通过查询当前最大版本来分配下一版本。没有缓存时，首版返回 `1`。

在并发请求下，两个请求可能同时完成以下动作：

```text
请求 A 查缓存：无
请求 B 查缓存：无
请求 A nextVersion：1
请求 B nextVersion：1
请求 A insert version=1：成功
请求 B insert version=1：唯一键冲突
```

## 5. 影响范围

- 后端接口：`GET /api/records/{recordId}/analysis`
- Java 服务：
  - 报告分析缓存读取与生成
  - `generated_outputs` 写入
  - API 异常处理
- 数据库表：
  - `generated_outputs`
- 前端和 agent 调用场景：
  - 页面打开记录详情后自动拉取分析
  - 记录切换时重复触发分析请求
  - agent 页面携带 `recordId` 时加载上下文或分析
  - 开发环境 React 严格模式或重复 effect 导致双请求

## 6. 根因分析

当前问题不是唯一约束设计错误。`UNIQUE (record_id, type, version)` 能防止同一记录同一类型同一版本出现重复数据，是合理的数据约束。

真正的问题是：应用层把“缓存未命中时生成首版分析”做成了非原子的先查后插流程，且没有处理数据库唯一约束反馈。

数据库已经用唯一约束告诉应用层“同一版本已经存在”。应用层应该把这个结果视为并发成功的一种表现，回查并返回已有结果，而不是让异常继续冒泡成 500。

`context not ready` 属于另一类状态：

```text
parseStatus != SUCCESS
或 structuredResult 为空
或 structuredResult.payload.fields 为空
```

它说明记录还不能分析，应返回 409 `ANALYSIS_NOT_READY`。它不是 `DuplicateKeyException` 的直接原因，但在上传报告后立刻打开页面、切换记录或进入 agent 时，两类日志可能在同一时间窗口出现。

## 7. 短期治理方案

1. 在报告分析生成落库处捕获 `DuplicateKeyException`。
2. 捕获后重新查询 `generated_outputs` 中该 `recordId + REPORT_ANALYSIS` 的最新记录。
3. 如果查到结果，返回 `cached=true` 的 `ReportAnalysisResult`，避免 500。
4. 如果仍查不到结果，再保留异常或转成明确的服务端错误。
5. 增加并发回归测试，模拟两次请求同时插入 `version=1` 时第二次能回查缓存返回。

该方案改动最小，可以快速止血，但仍可能重复调用 agent。

## 8. 中期治理方案

1. 将插入改为数据库级幂等：

```sql
insert into generated_outputs (...)
values (...)
on conflict (record_id, type, version) do nothing
```

2. 插入影响行数为 0 时，回查最新记录返回。
3. 对 `REPORT_ANALYSIS` 这类缓存型生成结果，评估是否只允许每个 `record_id + type` 生成一个当前有效版本。
4. 如仍保留多版本语义，使用数据库事务锁、行级锁或 PostgreSQL advisory lock 保护同一 `recordId + type` 的版本分配。
5. 增加接口层或服务层单飞机制，减少同一 JVM 内重复调用 agent。

## 9. 长期治理方案

1. 将报告分析生成从 GET 接口中拆出为明确任务模型：
   - 查询接口只读返回已有分析或生成状态。
   - 生成接口或后台任务负责创建分析。
2. 增加生成状态：
   - `NOT_STARTED`
   - `GENERATING`
   - `READY`
   - `FAILED`
3. 增加生成任务幂等键，例如 `recordId + type + schemaVersion`。
4. 建立可观测性指标：
   - 分析缓存命中率
   - agent 生成耗时
   - 同一记录并发生成次数
   - 唯一键冲突次数
   - `ANALYSIS_NOT_READY` 次数
5. 对前端请求做去重，避免页面组件重复触发同一记录的分析请求。

## 10. 验收标准

- 并发请求同一条记录的 `/analysis` 时，不再返回 500。
- 如果一个请求已经成功写入 `REPORT_ANALYSIS version=1`，其他并发请求能回查并返回该结果。
- `context not ready` 继续返回 409 `ANALYSIS_NOT_READY`，不被误处理为生成失败。
- 数据库唯一约束继续保留，不能通过删除约束规避问题。
- 日志能区分解析上下文未就绪、agent 生成失败、缓存写入并发冲突三类情况。
- 有针对性测试覆盖缓存命中、未就绪、生成成功、并发唯一键冲突回查四类场景。

## 11. 风险与注意事项

- 不应删除 `generated_outputs_record_id_type_version_key` 唯一约束，否则会引入重复版本数据。
- 只在前端去重不能解决问题；后端接口仍必须具备重复请求和并发请求下的幂等能力。
- 简单捕获所有数据库异常并回查会掩盖真实数据库故障，短期修复只应处理明确的唯一键冲突。
- 如果在生成前加锁，需要避免锁覆盖外部 agent 调用时间过长导致吞吐下降。
- 如果采用 `ON CONFLICT DO NOTHING`，需要明确插入失败后的回查策略和响应语义。

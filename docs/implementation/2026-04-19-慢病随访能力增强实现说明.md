# 慢病随访能力增强实现说明

## 文档信息

- 版本：v1.0
- 编写日期：2026-04-19
- 适用范围：`backend-java`、`backend-agent`、`frontend`
- 对应目标：将项目从“单次报告解读”增强为“面向慢病患者的随访型医疗 Agent MVP”

---

## 1. 背景与目标

本次改造的核心目标，不是继续扩展开放式聊天，而是围绕慢病患者的连续管理，把系统能力补齐到“可形成行动闭环”的程度。

改造前，系统已经具备以下基础能力：

- 检验/检查报告上传与解析
- 指标归一化与异常识别
- 组合异常分析
- 趋势上下文展示
- Agent 问答与多轮对话
- 患者数据权限与疾病档案隔离

本次改造后，系统进一步补齐了以下能力层：

- 明确工作流的随访型 Agent 对话
- 长期慢病画像与结构化医疗记忆
- 随访任务与症状/体征记录
- 风险监测与红旗信号优先提示
- 建议依据、证据类型与回答可信表达

本次实现定位为面向患者侧的差异化 MVP，不包含院内医生工作站、多患者运营后台或完整医学知识库 RAG。

---

## 2. 总体方案概览

本次实现围绕三条主线展开：

| 主线 | 目标 | 涉及模块 |
|------|------|----------|
| 长期慢病画像 | 把诊断、用药、过敏、随访目标等信息沉淀为长期上下文 | `backend-java`、`backend-agent`、`frontend` |
| 行动闭环 | 在解读后生成随访任务、复诊准备、风险提醒 | `backend-java`、`frontend` |
| 安全可信表达 | 强化红旗信号、证据来源、回答结构与工作流提示 | `backend-agent`、`frontend` |

整体信息流如下：

1. `backend-java` 提供慢病画像、随访任务、症状日志、风险概览和证据引用接口。
2. `backend-java` 的 Agent 上下文聚合接口把长期慢病信息并入疾病档案上下文。
3. `backend-agent` 读取增强后的上下文，改写 system prompt、上下文提示和 workflow prompt。
4. `frontend` 新增“慢病驾驶舱”视图与工作流切换 UI，把慢病画像、风险、任务、症状与对话放到一个工作台里。

## 3. 后端 Java 改动说明

### 3.1 数据库表结构新增

新增迁移文件：

- `backend-java/src/main/resources/db/migration/V10__patient_care_support.sql`

新增三张表：

| 表名 | 作用 | 关键字段 |
|------|------|----------|
| `patient_care_profiles` | 存储患者长期慢病画像 | 诊断、过敏史、异常基线、医生交代事项、健康目标、红旗备注、当前用药 |
| `follow_up_tasks` | 存储随访任务 | 标题、优先级、截止日期、状态、关联疾病档案/报告 |
| `symptom_logs` | 存储症状/体征记录 | 指标名、值、单位、风险级别、备注、记录时间 |

本次设计选择“轻量结构化持久化”而不是一开始引入复杂事件流或知识图谱，原因如下：

- MVP 更关注连续管理体验，而不是高度智能推理基础设施
- 这些数据天然适合作为 Agent 的长期记忆输入
- 前端能够直接消费，便于快速形成完整产品闭环

### 3.2 新增实体与 Mapper

新增实体：

- `PatientCareProfileEntity`
- `FollowUpTaskEntity`
- `SymptomLogEntity`

新增 Mapper：

- `PatientCareProfileMapper`
- `FollowUpTaskMapper`
- `SymptomLogMapper`

这些对象负责完成慢病驾驶舱相关数据的持久化读写，与既有的报告和疾病档案体系并行工作，不影响原有记录模型。

### 3.3 新增 DTO

请求 DTO：

- `UpdatePatientCareProfileRequest`
- `CreateFollowUpTaskRequest`
- `UpdateFollowUpTaskRequest`
- `CreateSymptomLogRequest`

响应 DTO：

- `PatientCareProfileResponseData`
- `PatientCareFollowUpTaskListResponseData`
- `PatientCareSymptomLogListResponseData`

DTO 层面的目标是把“慢病画像”“任务”“症状”“风险”和“证据”作为明确的产品对象暴露出来，而不是继续复用通用 map 结构。

### 3.4 新增服务 `PatientCareService`

新增文件：

- `backend-java/src/main/java/com/medical/agent/application/PatientCareService.java`

该服务是本次慢病随访能力的核心聚合层，负责：

- 获取与保存长期慢病画像
- 列出、创建、更新随访任务
- 列出、创建症状/体征日志
- 生成风险概览
- 生成证据引用列表

风险概览的计算逻辑主要来自四类输入：

| 输入来源 | 说明 |
|----------|------|
| 长期慢病画像 | 红旗备注、既往异常基线、医生交代事项 |
| 报告分析结果 | 联动异常、组合分析、当前记录异常 |
| 趋势数据 | 连续异常、恶化趋势、变化速率提示 |
| 随访任务/症状日志 | 任务逾期、症状告警等级 |

当前实现采用启发式规则完成风险分层，输出级别包括：

- `routine`
- `watch`
- `warning`
- `alert`

### 3.5 新增控制器 `PatientCareController`

新增文件：

- `backend-java/src/main/java/com/medical/agent/api/PatientCareController.java`

新增接口如下：

| 方法 | 路径 | 作用 |
|------|------|------|
| `GET` | `/api/patient-care/profile` | 获取慢病画像 |
| `PUT` | `/api/patient-care/profile` | 更新慢病画像 |
| `GET` | `/api/patient-care/follow-up-tasks` | 查询随访任务 |
| `POST` | `/api/patient-care/follow-up-tasks` | 新建随访任务 |
| `PATCH` | `/api/patient-care/follow-up-tasks/{taskId}` | 更新任务状态或内容 |
| `GET` | `/api/patient-care/symptoms` | 查询症状/体征日志 |
| `POST` | `/api/patient-care/symptoms` | 新建症状/体征记录 |
| `GET` | `/api/patient-care/risk-overview` | 获取风险概览 |
| `GET` | `/api/patient-care/evidence` | 获取证据引用 |

这些接口共同支撑了前端“慢病驾驶舱”的产品形态。

### 3.6 Agent 上下文聚合接口扩展

修改文件：

- `AgentDiseaseProfileContextResponse.java`
- `AgentDiseaseProfileContextService.java`

在既有疾病档案上下文的基础上，新增以下字段：

- `patientBaseline`

## 4. Python Agent 服务改动说明

### 4.1 上下文服务扩展

这样处理后，Python 侧不需要依赖 Java 返回字段的命名风格，可以统一使用 snake_case。

### 4.2 Context System Message 增强

修改文件：

- `backend-agent/app/agent/context.py`

本次改动把上下文提示从“报告信息渲染器”升级为“慢病管理上下文构造器”。新增输出内容包括：

- 已知慢病/诊断
- 过敏/禁忌
- 既往异常基线
- 医生交代事项
- 当前用药
- 当前健康目标
- 随访任务
- 红旗信号
- 证据来源

同时新增了动态引导规则：

- 如果存在用药信息，提示回答时优先引用当前用药
- 如果存在红旗信号，提示先判断是否需要尽快就医/复诊
- 如果存在证据引用，提示回答必须区分“已知事实 / 可能解释 / 建议动作”

这部分改造的目的，是让模型在进入主推理前就被“框进”慢病随访语境，而不是把这类上下文交给模型自行联想。

### 4.3 System Prompt 重写

修改文件：

- `backend-agent/app/prompts/system.py`

角色定位从：

- 专业的医疗 AI 助手

升级为：

- 专业的慢病随访医疗 AI 助手

新增或强化的规范包括：

- 默认采用 `已知事实 -> 可能解释 -> 建议动作` 三层结构
- 在报告解读和复诊准备场景下输出结构化行动闭环
- 把用药、过敏、任务、医生交代事项视为长期事实
- 区分规则结论、趋势推断、长期画像记忆和用户描述
- 给出建议时尽量附带依据类型和定性置信度
- 对胸痛、呼吸困难、禁忌等高风险场景优先输出就医分诊建议

这样修改后，模型在语言层面更符合医疗安全表达要求，也更符合产品定位。

### 4.4 Workflow Prompt 扩展

修改文件：

- `backend-agent/app/prompts/templates.py`
- `backend-agent/app/agent/nodes.py`

本次新增/强化三个固定工作流：

| workflow | 产品语义 | 主要用途 |
|----------|----------|----------|
| `report_interpretation` | 报告解读 | 解读当前报告异常、趋势和联动异常 |
| `follow_up_prep` | 复诊准备 | 输出复诊前准备清单、复查建议、要问医生的问题 |
| `medication_review` | 用药回顾 | 结合长期用药和报告指标做回顾分析 |

`nodes.py` 中的 LLM 调用逻辑，已从只识别 `scenario` 改为同时识别：

- `workflow`
- `scenario`
- `audience`
- `urgency_level`

这让同一套 Agent 服务具备更明确的“产品工作流意识”。

### 4.5 Chat Schema 扩展

修改文件：

- `backend-agent/app/schemas/chat.py`
- `backend-agent/app/agent/state.py`

聊天元数据新增字段：

- `workflow`
- `urgency_level`
- `audience`

这些字段会随着前端请求进入 Agent 推理链路，并成为 prompt 决策的一部分。

## 6. 构建稳定性与类型修复

在完成功能实现后，本次又补了两类“工程层”的修复，以确保新增能力能够真正稳定构建和维护。

### 6.1 TypeScript 类型闭环修复

修改文件：

- `frontend/src/components/agent/useSessionManager.ts`
- `frontend/src/components/agent/useAgentWorkbench.ts`
- `frontend/src/components/agent/useCareSupport.ts`

修复内容包括：

- `selectSession()` 返回值增加 `lastTurnMetadata`，用于恢复历史会话的 workflow
- `useAgentWorkbench` 改为读取 `lastTurnMetadata`，不再错误访问不存在的 `turns`
- `useCareSupport` 中对数组字段的归一化改成更明确的局部变量和显式类型，避免 TS 把联合表达式推断成 `{}` 导致 `.map()` 报错

### 6.2 前端类型依赖补齐

变更内容：

- 为 `frontend` 增加 `@types/react-dom`

原因：

- `AppSelect.tsx` 使用了 `createPortal`
- 原项目缺少 `react-dom` 的类型定义，导致 `tsc --noEmit` 无法通过

### 6.3 去除 Google Fonts 构建依赖

修改文件：

- `frontend/src/app/layout.tsx`

问题：

- `next/font/google` 会在构建阶段请求 Google Fonts
- 当前环境的代理变量配置异常，导致生产构建失败
- 这类依赖也会让离线环境、内网环境和 CI 环境变得脆弱

修复方式：

- 移除 `next/font/google` 的在线字体加载
- 直接使用 `globals.css` 中已经定义好的本地字体栈变量

收益：

- 前端构建不再依赖外网字体服务
- 本地和 CI 的构建稳定性更高
- 不影响当前页面字体风格的基本表达

## 8. 产品层面带来的实际变化

从产品视角看，这次改造带来的变化可以概括为以下几点：

### 8.1 从“问一次答一次”变成“围绕患者持续管理”

以前的上下文中心是“当前报告”。

现在的上下文中心变成了“当前患者的慢病管理状态”，报告只是其中一个观察点。

### 8.2 从“解释结果”变成“推动下一步动作”

现在系统不仅能解释异常，还能沉淀：

- 随访任务
- 复诊准备
- 风险等级
- 症状跟踪

### 8.3 从“模型自己发挥”变成“工作流明确约束”

通过 workflow、urgency、audience 和 context guidance，模型被更清晰地约束在不同产品场景下说什么、怎么说、先说什么。

### 8.4 从“看起来像医疗”变成“更接近医疗产品的安全表达”

现在回答会更强调：

- 已知事实
- 可能解释
- 建议动作
- 紧急程度
- 建议依据

这比单纯生成“像医生说话”的文本更可靠。

## 9. 当前未覆盖的范围

本次没有实现以下能力，属于明确的后续项：

- 完整医学知识 RAG 或指南检索
- 患者版 / 照护者版 / 专业版多角色回答视图
- 真正的消息提醒/自动提醒调度
- 多患者批量管理
- 复杂疾病特异性的分层策略引擎

这些能力可以在现有慢病画像、风险概览和 workflow 元数据基础上继续演进。

## 10. 后续建议

建议下一阶段按以下顺序继续推进：

1. 把风险概览里的启发式规则进一步疾病化，优先补糖尿病、高血压、肾病三类随访规则。
2. 为 `evidence_refs` 接入轻量知识检索，让“依据来源”不止来自本地规则和趋势摘要。
3. 在前端补充“复诊准备清单导出”或“下一次复查提醒”能力，把任务闭环做完整。
4. 为 `audience` 增加患者版和专业版回答差异化模板，为第二阶段多角色协同预留空间。

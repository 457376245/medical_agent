## 元数据

## 摘要

在现有单指标异常判定（`resultState=high/low/threshold`）基础上，新增指标名归一化和组合联动分析能力。通过将不同医院报告中的指标名映射到统一编码，再用声明式规则匹配指标组合异常模式，使系统能识别出"AST/ALT 比值 >2 + GGT 升高 → 酒精性肝损伤倾向"这类单看单个指标无法发现的临床有意义的组合异常。

## 背景和目标

- **业务背景**：用户上传的体检/检验报告包含大量结构化字段，当前系统只做逐项高低判定。但临床实践中，多项指标的组合模式往往比单项异常更有诊断指向性。
- **用户痛点**：普通用户看到多个指标偏高/偏低时，不知道它们之间的关联意义，只能逐项查搜索引擎。
- **成功标准**：
  - 能将 95%+ 的常见体检指标名映射到统一编码
  - MVP 阶段覆盖肝功能、肾功能、糖代谢、甲状腺 4 个系统共 10 条联动规则
  - 记录详情接口能返回命中的组合分析结果
  - 报告分析 LLM 链路能引用已确认的组合模式生成解读

## 范围

### 范围内

- 指标名归一化：自定义精简编码体系（~150 个核心指标），三层匹配策略
- 组合规则引擎：声明式 YAML 规则，支持 state/value/ratio 三种条件类型
- API 响应扩展：记录详情接口增加 `combinationAnalysis` 字段
- LLM 上下文增强：将规则触发结果作为 REPORT_ANALYSIS 上下文

### 范围外

- 纵向趋势联动（跨次报告的指标变化组合）→ V2
- 前端组合分析展示组件 → 独立任务
- 用药-指标关联分析 → 独立特性
- 医学诊断或用药建议 → 不做

## 模块一：指标名归一化

### 编码体系

采用自定义精简编码（全大写英文缩写作为 key），覆盖常规体检 + 常见慢病随访的 ~150 个核心指标。

分类范围：血常规（~20）、肝功能（~12）、肾功能（~6）、血脂（~8）、糖代谢（~8）、甲状腺（~8）、电解质（~6）、肿瘤标志物（~12）、尿常规（~12）、凝血功能（~6）、感染/炎症（~6）、乙肝/传染病（~12）、心肌标志物（~5）、骨代谢（~5）、性激素（~6）、自免/其他（~10）。

### 单指标元数据结构

```yaml
# indicator_catalog.yaml 示例
ALT:
  displayName: "丙氨酸氨基转移酶"
  shortName: "谷丙转氨酶"
  category: "肝功能"
  commonUnit: "U/L"
  aliases:
    zh: ["谷丙转氨酶", "丙氨酸氨基转移酶", "谷丙", "丙氨酸转氨酶"]
    en: ["ALT", "SGPT", "GPT", "Alanine aminotransferase"]
    mixed: ["谷丙转氨酶(ALT)", "ALT(谷丙转氨酶)"]
```

### 三层匹配策略

| 优先级 | 策略 | 说明 |
|--------|------|------|
| 1 | 精确匹配 | trim + lowercase 后查 alias 索引 |
| 2 | 括号拆分 | 提取 `()` / `（）` 内外部分，分别精确匹配 |
| 3 | 包含匹配 | 输入包含某 alias 或某 alias 包含输入 |
| 4 | 英文 token 提取 | 从混合文本中提取连续英文字母，再匹配 |
| 5 | LLM fallback | 前 4 步均未命中时调 LLM 映射（可选，初期可不实现） |

**不使用编辑距离**：中文指标名长度差异大，"谷丙"与"谷草"编辑距离仅 1 但完全不同，假阳性过高。

### 与 parse 提示词的配合

在 parse 提示词中新增指令，让 LLM 尝试输出 `standardCode` 字段。Java 侧验证该 code 是否在编码表中：在表中则采用，不在表中则走规则匹配链。

### UNMAPPED 处理

不阻塞流程。UNMAPPED 指标照常展示和判定，仅不参与联动分析。后台可按 UNMAPPED 原始 name 出现频次统计，高频项人工补录到同义词表。

### 技术实现

```
backend-java/
├── src/main/resources/
│   └── indicator_catalog.yaml
├── src/main/java/.../domain/service/
│   ├── IndicatorCatalog.java        // 加载 YAML，构建 exactIndex + substringIndex
│   └── IndicatorNormalizer.java     // 执行归一化匹配
└── src/main/java/.../application/service/
    └── StructuredFieldInterpreter.java  // enrichFieldInPlace 中调用归一化
```

## 模块二：组合联动规则引擎

### 规则数据结构

```yaml
# combination_rules.yaml 示例
- id: "LIVER_ALCOHOLIC_PATTERN"
  name: "酒精性肝损伤模式"
  category: "肝功能"
  severity: "warning"              # info / warning / alert
  description: "AST/ALT比值>2且GGT升高，提示酒精性肝损伤倾向"
  requiredIndicators: ["AST", "ALT", "GGT"]
  conditions:
    - type: "ratio"
      numerator: "AST"
      denominator: "ALT"
      operator: ">"
      threshold: 2.0
    - type: "state"
      indicator: "GGT"
      resultState: "high"
  interpretation:
    summary: "您的肝功能指标呈现酒精性肝损伤模式"
    detail: "AST/ALT比值为{ratio}（>2），同时GGT偏高（{GGT_value}{GGT_unit}），这种组合常见于酒精性或药物性肝损伤。"
    suggestion: "建议减少饮酒并咨询消化内科或肝病科医生。"
```

### 条件类型

| 类型 | 说明 | MVP |
|------|------|-----|
| `state` | 指标的 resultState 是否为指定值 | ✅ |
| `value` | 指标数值与阈值比较 | ✅ |
| `ratio` | 两个指标的比值与阈值比较 | ✅ |
| `trend` | 同一指标连续多次的变化趋势 | V2 |
| `presence` | 某指标是否存在 | V2 |

### 执行流程

```
enrichPayload() → normalizeIndicators() → CombinationAnalyzer.analyze()
                                              │
                              构建 indicatorMap (standardCode → field)
                                              │
                              遍历规则 → 检查 requiredIndicators → 评估 conditions
                                              │
                              输出 List<TriggeredRule>
```

### MVP 规则清单（10 条）

| ID | 名称 | 条件 |
|----|------|------|
| LIVER_ALCOHOLIC | 酒精性肝损伤模式 | AST/ALT > 2 + GGT↑ |
| LIVER_CHOLESTASIS | 胆汁淤积模式 | ALP↑ + GGT↑ + ALT 正常 |
| LIVER_HEPATOCELL | 肝细胞损伤模式 | ALT↑ + DBIL↑ |
| RENAL_DECLINE | 肾功能减退信号 | CREA↑ + BUN↑ |
| RENAL_PRERENAL | 肾前性异常 | BUN↑ + CREA 正常 |
| DM_PREDIABETES | 糖尿病前期风险 | GLU ∈ [6.1, 7.0) 或 HBA1C ∈ [5.7, 6.5) |
| DM_UNCONTROLLED | 血糖控制不佳 | HBA1C > 7.0 |
| THYROID_HYPO | 甲减模式 | TSH↑ + FT4↓ |
| THYROID_HYPER | 甲亢模式 | TSH↓ + FT4↑ |
| THYROID_SUBCLINICAL | 亚临床甲状腺异常 | TSH 异常 + FT3 正常 + FT4 正常 |

### API 响应扩展

在 `/api/records/{recordId}` 返回体中新增：

```json
{
  "structuredResult": {
    "payload": { "fields": [...] },
    "combinationAnalysis": [
      {
        "ruleId": "LIVER_ALCOHOLIC",
        "name": "酒精性肝损伤模式",
        "severity": "warning",
        "summary": "...",
        "detail": "...",
        "suggestion": "...",
        "involvedIndicators": ["AST", "ALT", "GGT"]
      }
    ]
  }
}
```

### LLM 上下文增强

将 `combinationAnalysis` 结果作为 `REPORT_ANALYSIS` 任务的上下文，LLM 的角色从"判断者"变为"翻译者"——规则确定有什么组合异常，LLM 负责生成通俗自然的解读文案。

### 技术实现

```

├── src/main/resources/
│   └── combination_rules.yaml
├── src/main/java/.../domain/service/
│   ├── CombinationRule.java         // 规则 POJO
│   ├── RuleCondition.java           // 条件类型（state/value/ratio）
│   ├── TriggeredRule.java           // 触发结果 VO

└── src/main/java/.../application/service/

```

## 风险与注意事项

- **免责声明必须到位**：所有组合分析结论必须标注"仅供参考，不构成医疗诊断建议"
- **规则需医学审核**：10 条 MVP 规则的阈值和结论文案需要有医学背景的人审核
- **归一化冷启动**：第一版别名库不完整，UNMAPPED 率可能在 15-20%，需通过 UNMAPPED 统计持续迭代
- **性能影响**：规则评估是纯内存操作，10 条规则对延迟影响可忽略

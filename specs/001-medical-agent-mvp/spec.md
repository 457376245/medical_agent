## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传并生成本次结果 (Priority: P1)

作为患者或家属，我可以上传检查单图片或 PDF，并在一次处理完成后获得结构化检查结果和可读摘要，从而减少手工整理。

**Why this priority**: 这是核心价值闭环的入口与结果，没有该能力则无法证明 MVP 的基础可用性。

**Independent Test**: 仅实现该故事即可独立验证价值：上传有效文件后，用户能看到结构化字段与摘要，并可区分成功/失败状态。

**Acceptance Scenarios**:

1. **Given** 用户已进入上传页面且文件格式为 jpg/png/pdf，**When** 提交单个文件，**Then** 系统接收文件并创建处理任务，显示处理中状态。
2. **Given** 处理任务完成，**When** 用户打开该次记录，**Then** 可查看结构化检查字段（项目、数值、单位、参考范围、结论）和本次检查结果摘要。
3. **Given** 文件损坏或无法识别，**When** 处理失败，**Then** 系统给出明确失败原因与重试入口，不生成误导性结果。

---

### User Story 2 - 生成用药计划草案 (Priority: P2)

作为患者或家属，我可以在完成解析后获得基于文档内容整理出的用药计划草案，便于执行与复诊沟通。

**Why this priority**: 该能力直接提升用药信息清晰度，是高频复用场景，但依赖基础解析能力，所以优先级次于 P1。

**Independent Test**: 在已有解析结果前提下，独立验证可读且结构化的用药计划草案是否生成，并包含来源提醒与免责声明。

**Acceptance Scenarios**:

1. **Given** 解析结果中包含药品相关信息，**When** 用户查看该次记录，**Then** 系统生成并展示药品名称、剂量、频次、时段等草案内容。
2. **Given** 文档中无完整用药字段，**When** 生成草案，**Then** 系统明确标注缺失项并提示用户补充或确认。
3. **Given** 用户查看任何 AI 生成内容，**When** 页面展示结果，**Then** 必须同时显示“仅供参考，不替代医生建议”的提示。
4. **Given** 用户准备保存用药计划草案，**When** 点击保存，**Then** 系统必须要求用户显式二次确认后才允许保存。

---

### User Story 3 - 病症时间轴回看与解析结果查看 (Priority: P3)

作为患者或家属，我可以在上传时选择或新增病症，并在病症时间轴上回看每次报告的解析结果，以便持续追踪病情发展。

**Why this priority**: 该能力直接服务“按病症长期管理”目标，是复诊准备和病情追踪的核心体验。

**Independent Test**: 在同一病症下上传多条不同日期报告后，用户可在病症时间轴按日期查看并点击进入每条报告的解析结果详情。

**Acceptance Scenarios**:

1. **Given** 用户上传报告，**When** 未选择病症，**Then** 系统阻止上传并要求先选择或新增病症。
2. **Given** 同一病症下有多份报告，**When** 用户查看病症时间轴，**Then** 系统按报告日期倒序展示节点。
3. **Given** 用户点击时间轴某节点，**When** 打开详情，**Then** 系统展示该报告的解析后数据而非原始图片/PDF。

---

### User Story 4 - 数据导出与删除请求 (Priority: P2)

作为患者或家属，我可以发起个人医疗数据导出与删除请求，并查看处理状态，从而满足合规与个人数据权利诉求。

**Why this priority**: 该能力是合规底线要求，属于上线前必须具备的受理入口能力。

**Independent Test**: 用户可发起导出和删除请求，系统返回请求 ID 与状态；请求动作被审计记录，且仅授权用户可见。

**Acceptance Scenarios**:

1. **Given** 用户已登录并进入记录详情，**When** 发起导出请求，**Then** 系统创建导出任务并返回可追踪状态。
2. **Given** 用户已登录并进入记录详情，**When** 发起删除请求，**Then** 系统创建删除请求并返回受理状态与审计记录。
3. **Given** 非记录所有者尝试访问导出/删除请求，**When** 发起操作，**Then** 系统拒绝请求并返回权限错误。

---

### Edge Cases

- 用户一次上传多个大文件时，任务进入队列但仍需可见进度与最终状态，避免“静默失败”。
- OCR 仅识别出部分字段时，系统需输出“部分可用”结果并标记缺失字段，不可伪造完整信息。
- 重复上传相同材料时，系统应提示疑似重复并允许用户确认是否继续创建新记录。
- 文件格式正确但内容非医疗资料时，系统需拒绝生成医疗摘要并给出原因。
- 用户在处理中离开页面后再次进入，仍能看到任务状态与最终结果。
- 结构化结果中低置信字段必须展示来源证据（来源文件/页码/文本片段），并允许用户修订后保存新版本。
- 用户发起删除请求后，系统需在请求状态中可见处理进度，避免“已提交但无反馈”。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许患者或家属上传医疗材料，支持 `jpg`、`png`、`pdf` 三种输入格式，且上传前必须选择已有病症或新增病症。
- **FR-002**: 系统 MUST 为每次上传创建可追踪的处理任务，并向用户展示至少“已提交、处理中、成功、失败”四种状态。
- **FR-003**: 系统 MUST 从上传材料中提取并结构化检查信息，至少包括检查项目、结果数值、单位、参考范围、结论；对低置信字段必须提供来源证据（来源文件、页码或文本片段）并支持用户修订。
- **FR-004**: 系统 MUST 在单次处理完成后生成“检查结果摘要”，且摘要需可读、可回看、与原始记录关联。
- **FR-005**: 系统 MUST 基于已提取的用药信息生成“用药计划草案”，至少包括药品名称、剂量、频次与适用时段（若可识别）。
- **FR-006**: 系统 MUST 在任何 AI 生成结果展示位置提供明确免责声明，说明内容仅供参考且不替代医生诊疗意见。
- **FR-007**: 用户 MUST 能查看单次上传记录的完整内容，包括原始材料、结构化结果、摘要与用药草案。
- **FR-008**: 系统 MUST 提供按病症聚合的时间轴视图，支持按报告日期浏览历史记录。
- **FR-009**: 系统 MUST 在解析失败或字段缺失时返回可理解的错误或缺失提示，并提供重试路径。
- **FR-010**: 系统 MUST 支持并发上传与任务排队；在 100 并发上传场景下任务创建成功率 >= 99%，队列入队失败率 < 0.5%。
- **FR-011**: 系统 MUST 对医疗数据实行传输与存储保护、最小权限访问控制，并记录关键操作审计日志。
- **FR-012**: 系统 MUST 对结构化输出使用可识别的版本标识，以保证后续字段演进时的兼容性。
- **FR-013**: 系统 MUST 保持中立数据语义；新增字段必须遵循向后兼容策略（v1 客户端无需改造即可继续读取既有字段）。
- **FR-014**: 系统 MUST 提供数据导出请求入口，用户可发起、查询导出请求状态，并在任务完成后通过受控下载方式获取导出结果。
- **FR-015**: 系统 MUST 提供数据删除请求入口，用户可发起删除请求并查询处理状态，删除相关操作必须进入审计日志。
- **FR-016**: 系统 MUST 提供显式摘要生成接口与状态反馈，并与记录及版本信息关联。
- **FR-017**: 系统 MUST 对 `PATCH /records/{recordId}/structured-result` 提供修订版本控制，保留修订历史并可追溯到操作者与时间。
- **FR-018**: 系统 MUST 在用药计划草案保存前要求用户显式二次确认；未确认时不得保存。
- **FR-019**: 系统 MUST 允许用户在时间轴点击任意报告节点并查看该报告的解析后数据详情。
- **FR-020**: 系统 MUST 默认展示解析后报告数据（结构化结果与摘要）；原始图片/PDF不得作为详情主视图。

### Non-Functional Requirements

- **NFR-001**: 所有外部 API 与服务间调用必须启用 TLS。
- **NFR-002**: 对象存储与数据库必须启用静态加密能力。
- **NFR-003**: 系统必须产出可观测指标以验证 SC-001~SC-006（上传成功率、任务完成率、P95 时延、关键字段准确率、摘要到达率、审计覆盖率）。
- **NFR-004**: 高风险流程（上传、解析、生成、保存、删除/导出、权限边界）必须有自动化测试覆盖，低风险变更必须有手工验收清单。

### Assumptions

- MVP 首发面向中国内地个人用户（患者与家属代管场景），以单用户管理单患者资料为主。
- 用药计划草案边界为“整理已有材料中的医嘱/用药信息”，不新增诊断或治疗建议。
- 数据处理遵循“默认不跨境传输”原则；如未来需跨境，另行评审并更新规范。
- MVP 优先保证“上传-解析-可读输出-可回看”闭环，医生审核工作流与医院深度对接不纳入当前范围。

### Key Entities *(include if feature involves data)*

- **用户账户**: 使用系统的患者或家属身份，具备访问本人管理资料和操作记录的权限边界。
- **医疗材料**: 用户上传的原始文件，包含文件类型、上传时间、所属批次、处理状态。
- **处理任务**: 针对单次上传触发的解析流程对象，包含任务状态、开始/完成时间、失败原因。
- **结构化检查结果**: 从原始材料提取的标准字段集合，包含版本标识与字段完整性标记。
- **检查结果摘要**: 面向用户阅读的检查结论说明，关联具体上传记录与生成时间。
- **用药计划草案**: 由材料中可识别用药信息整理得到的执行草案，包含免责声明与缺失项标记。
- **病症档案**: 用户管理的病症对象，作为上传归档与时间轴聚合主键。
- **病症时间轴条目**: 同一病症下按报告日期组织的历史节点，用于病情发展追踪。
- **审计记录**: 对上传、查看、生成、重试等关键操作的留痕记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户提交的医疗材料上传成功率不低于 98%。
- **SC-002**: 已提交处理任务的完成率不低于 95%（成功或明确失败均计为完成）。
- **SC-003**: 从提交上传到用户看到首版结果的端到端处理时延在 P95 下不超过 90 秒。
- **SC-004**: 抽样质检中，结构化关键字段（项目、数值、单位、参考范围、结论）准确率不低于 85%。
- **SC-005**: 至少 90% 的首次上传用户可在一次流程内获得可读检查摘要。
- **SC-006**: 关键数据访问与生成操作 100% 进入审计记录，且 MVP 阶段无高危隐私泄露事故。

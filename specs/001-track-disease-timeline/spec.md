# Feature Specification: 病症维度病历追踪与解析展示

**Feature Branch**: `001-track-disease-timeline`  
**Created**: 2026-02-07  
**Status**: Draft  
**Input**: User description: "我期望的是，用户上传资料时会要求选择对应的病症，可以添加，当用户上传资料并处理完后，对应病症会有一条时间轴，显示报告日期，并且可以点击并查看对应的报告数据，且报告数据应该是解析后的内容，而不是原始的图片或者pdf。以该业务为主线，修改对应的md记录"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按病症上传并解析报告 (Priority: P1)

用户上传检查资料时必须先选择一个已有病症，或新增病症后再上传。系统处理完成后，用户可以直接看到该报告的解析结果（结构化字段与摘要），而不是原始图片/PDF。

**Why this priority**: 这是核心价值链路。若无法“病症归档 + 解析可读结果”，项目无法支撑病情记录与管理目标。

**Independent Test**: 用户新增病症并上传一份报告，处理成功后在同一病症下能看到该报告的解析结果页面（包含结构化字段与摘要），且页面不依赖查看原始文件。

**Acceptance Scenarios**:

1. **Given** 用户在上传页，**When** 未选择病症直接提交上传，**Then** 系统阻止提交并提示先选择或新增病症。
2. **Given** 用户新增病症并上传报告，**When** 处理完成，**Then** 系统展示该报告的解析后内容（项目、结果值、单位、参考范围、结论、摘要）。
3. **Given** 解析结果存在低置信字段，**When** 用户查看结果，**Then** 系统高亮低置信字段并展示来源证据。

---

### User Story 2 - 病症时间轴跟踪病情发展 (Priority: P2)

用户进入某个病症后，可以看到该病症下按报告日期排序的时间轴，并能点击任意节点查看对应解析报告，用于观察病情变化趋势。

**Why this priority**: 该功能承接“长期追踪”目标，帮助用户理解同一病症的历史演进。

**Independent Test**: 在同一病症下准备多条不同日期报告，用户可在时间轴上看到按日期排序的节点，点击节点后显示对应解析后数据。

**Acceptance Scenarios**:

1. **Given** 同一病症下有多份报告，**When** 用户打开病症详情，**Then** 系统按报告日期显示时间轴节点。
2. **Given** 用户点击某时间轴节点，**When** 进入报告详情，**Then** 页面展示该报告的解析结果，而非原始文件。
3. **Given** 病症下暂无报告，**When** 用户打开病症详情，**Then** 系统展示空状态并引导上传首份资料。

---

### User Story 3 - 基于历史病情的 Agent 建议分析 (Priority: P3)

用户在 Agent 页面可基于某病症的历史解析记录获得趋势说明与建议，用于辅助理解病情变化与后续关注点。

**Why this priority**: 在“记录与追踪”基础上提供解释与建议，提升产品对用户的持续使用价值。

**Independent Test**: 用户选择一个有历史记录的病症后，可得到面向该病症历史数据的建议分析，并带有“仅供参考”提示。

**Acceptance Scenarios**:

1. **Given** 用户进入 Agent 页面并选择病症，**When** 发起分析，**Then** 系统返回基于该病症历史记录的分析建议。
2. **Given** 用户查看 Agent 建议，**When** 建议包含高风险内容（如用药相关），**Then** 页面明确显示“仅供参考，不替代医生建议”。

---

### Edge Cases

- 用户上传报告时选择了错误病症，系统应支持后续重新归档到正确病症并保留审计记录。
- 同一天同病症上传多份报告时，时间轴需稳定排序并可区分不同报告条目。
- 报告解析失败时，时间轴应显示失败节点状态并提供重试入口。
- 解析结果缺少关键字段时，报告详情必须标记“字段缺失”，避免误解为正常值。
- 历史记录不足（仅 1 条）时，Agent 页面应提示“趋势判断依据不足”。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在用户上传资料前要求选择病症；若无病症，用户 MUST 能新增病症后继续上传。
- **FR-002**: 系统 MUST 将每份上传报告绑定到一个且仅一个病症，并记录报告日期。
- **FR-003**: 系统 MUST 在处理完成后提供报告的解析后内容展示，包括结构化字段与摘要。
- **FR-004**: 系统 MUST 在病症详情页提供按报告日期组织的时间轴视图。
- **FR-005**: 用户 MUST 能从病症时间轴点击进入某份报告，并查看该报告的解析后内容。
- **FR-006**: 系统 MUST 区分“解析后结果视图”和“原始文件”，默认展示解析后结果。
- **FR-007**: 系统 MUST 在解析失败时保留报告记录并显示失败状态、失败原因及重试入口。
- **FR-008**: 系统 MUST 支持同一病症下多份报告的趋势查看，不得因新增报告覆盖历史结果。
- **FR-009**: 系统 MUST 提供 Agent 页面，允许用户基于某病症历史记录生成建议分析。
- **FR-010**: 系统 MUST 在 Agent 建议与所有生成内容页面显示“仅供参考，不替代医生建议”。
- **FR-011**: 系统 MUST 为病症新增、报告上传、结果查看、重试、归档调整等关键操作保留可追溯记录。

### Safety & Compliance Requirements *(mandatory for medical/high-sensitivity features)*

- **SCM-001**: 所有 AI 生成内容必须显示“仅供参考，不替代医生建议”的用户可见提示。
- **SCM-002**: 涉及用药相关建议时，最终保存或确认前必须有显式用户再确认行为。
- **SCM-003**: 病症、报告与解析数据在存储与访问环节必须遵循加密、最小权限和可审计原则。
- **SCM-004**: 合规区域默认假设为中国大陆个人健康信息场景；跨区域合规差异列为后续治理项。

### Reliability, Traceability & Versioning Requirements *(mandatory)*

- **RTV-001**: 报告处理流程必须定义异步状态、超时、重试和用户可见恢复动作。
- **RTV-002**: 低置信字段必须提供高亮、来源证据与可编辑确认路径。
- **RTV-003**: 病症时间轴与报告解析结果的版本变化必须可追溯，且不破坏历史可读性。
- **RTV-004**: 上传与生成流程必须定义防重复提交机制，避免重复创建同一任务。

### Key Entities *(include if feature involves data)*

- **DiseaseProfile（病症档案）**: 用户用于归档病历的病症对象，包含病症名称、创建时间、状态。
- **MedicalReport（医疗报告）**: 用户上传的单份资料记录，绑定病症并带有报告日期、处理状态。
- **ParsedReportResult（解析结果）**: 对应某份报告的结构化结果与摘要，包含关键字段、置信度、版本。
- **DiseaseTimelineEntry（病症时间轴条目）**: 病症维度的时间节点，关联报告日期、报告标识、处理状态。
- **AgentInsight（建议分析）**: 基于病症历史记录生成的分析建议内容，包含生成时间与风险提示标识。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 90% 以上用户可在首次使用时于 3 分钟内完成“选择病症并上传首份报告”。
- **SC-002**: 95% 以上处理成功的报告可在 5 秒内从时间轴节点打开并展示解析后结果。
- **SC-003**: 同一病症下连续上传 3 份以上报告的用户中，85% 能成功查看病症时间轴并完成至少一次历史对比。
- **SC-004**: 解析任务完成率达到 97% 以上（含重试成功），超时失败率低于 2%。
- **SC-005**: 100% 的生成内容页面展示“仅供参考”提示，且用药相关确认流程完成率达到 98% 以上。

### Mandatory Quality Signals

- 包含可靠性指标：任务完成率、超时失败率、重试成功率。
- 包含时延指标：从时间轴点击到解析结果展示的用户可感知时延。
- 包含安全/合规指标：免责声明覆盖率、用药建议再确认完成率。

## Assumptions

- 每份报告默认仅归属一个病症，跨病症共享通过复制归档实现。
- 病症时间轴默认按“报告日期”降序展示。
- 报告详情默认展示解析后结果；原始文件预览作为次级入口，不作为主展示。
- Agent 建议基于用户当前可访问的历史记录生成，不跨用户汇总数据。
